# DEPLOY.md - the deploy + release runbook

memstruct ships **two faces and one package**:

- `web/` - the landing site (Cloudflare Pages)
- `docs/` - the docs rig (GitHub Pages)
- the root `package.json` - the `memstruct` CLI on npm

Nothing here needs a database, a key, or a server.

## 1. The landing (`web/`, prestruct)

The build command is `prestruct build` (via `npm run build --prefix web`); it
compiles the app graph, prerenders **every route** into
`web/dist/<route>/index.html`, and injects the brand meta from
`web/ssr.config.js`.

**Cloudflare Pages project settings** (dashboard-side - there is no root
`wrangler.toml`, the contract lives here and in the dashboard, exactly like
crashtest's and packstruct's):

| setting | value |
| --- | --- |
| root directory | `web` |
| build command | `npm run build` |
| output directory | `dist` |

Healthy = the build's last line reads `N/N pages rendered` with N equal to your
routes. That is the same gate `test.yml` runs.

`web/public/_headers` and `web/public/_redirects` ship the CSP and the
do-NOT-SPA-fallback wisdom (with prerendering, every route has its own
`dist/<route>/index.html`, so the catch-all rewrite would loop).

## 2. The docs (`docs/`, Jekyll + pagefind)

GitHub Pages territory: `.github/workflows/docs-deploy.yml` is a thin caller of
THE one docs lane (`dhaupin/freestruct`'s `.github/workflows/docs-lane.yml`),
which runs gates -> Jekyll -> freestruct (pinned) -> pagefind -> Pages artifact
upload. `docs/_config.yml` (`url` + `baseurl`) is GENERATED by the coreforge
shell's `sync` verb from `site.config.js` - edit that file, then re-run that
verb. The `paths:` filter means the workflow only fires on `docs/**` changes.

The docs lane is one canonical reusable workflow owned by `dhaupin/freestruct`;
this repo keeps only a thin caller that pins the lane by SHA and grants
`pages: write` + `id-token: write`. Set the Pages custom domain
(`docs.creadev.org`) once in the repo's Pages settings.

## 3. The staging branch

`staging` is a permanent integration branch: work branches off it, PRs target
it, and promotion to `main` is the only path out. `test.yml` pushes on both
`main` and `staging`, so a red battery red-lights the integration branch before
a promotion. `docs-deploy.yml` builds on `staging` too but its deploy job is
gated to `main` (the lane's own guard).

After every promotion, fast-forward staging to main:

```bash
git push origin origin/main:staging     # ff, non-destructive
```

`.github/workflows/staging-ff-sync.yml` does this automatically after a push to
`main`.

## 4. Release (npm + GitHub release)

The version protocol: bump `package.json` (and `web/package.json` when the site
changes) in the SAME commit as the `CHANGELOG.md` entry -> commit -> tag
`vX.Y.Z` -> push the tag. `.github/workflows/publish.yml` publishes via npm
Trusted Publishing (OIDC, no `NPM_TOKEN` secret, provenance signed) and runs
the same `npm run check` battery as `prepublishOnly`.

- 0.x is refused by the OIDC lane; 0.x ships by hand.
- One-time setup: link the package to this repo under npmjs.com -> package
  Settings -> Publishing access.
- If a tag-driven run fails, re-push the tag for the retry:
  `git push origin :refs/tags/vX.Y.Z && git push origin vX.Y.Z`.

## 5. The phone ship lane

`scripts/ship-from-download.cjs` stages a GitHub zip-extracted tree inside the
Termux home and publishes it (the Termux recipe, scripted). It is
family-reusable and product-agnostic:

```bash
NPM_TOKEN=<token> node scripts/ship-from-download.cjs \
  --target /storage/emulated/0/Download/memstruct-main/memstruct-main \
  --root ~/web/memstruct-main               [--dry-run] [--clean]
```

The repo's own `prepublishOnly` gate still rules; the ship script only gets the
tree to the launchpad. Tested by `test/ship-from-download.test.cjs`.

## 6. Local checks before any push

```bash
npm run check          # the battery: tests + language + pins + spec + docs + conformance
npm run lint:docs      # the docs truth gates alone
npm install --prefix web && npm run build --prefix web   # the landing, for real
```

Docs builds are CI's job locally-optional (Jekyll is too much runtime to
demand); the deploy workflow is the truth.
